Практическая «Оптимизация для мобильных устройств» — ответы и ожидаемые значения
(замерено в эмуляции iPhone SE: 375 точек, DPR 2; на компьютерах студентов числа будут того же порядка)

Шаг 1. Без viewport телефон рисует страницу шириной ~1000 точек: всё мелкое. Жёсткие пиксели в «РАСКЛАДКЕ»:
       .header width: 1000px, .page width: 1000px, .list 300px 300px 300px.
Шаг 2. Две колонки — от 640 точек, три — от 1000. Без медиазапроса написаны правила для телефона,
       в @media (min-width) — добавки для широких экранов.
Шаг 3. Кнопка «Отправить»: до — ~20 px высотой, после — 48 px. Поле «Сколько человек» (type="number",
       inputmode="numeric") открывает цифровую клавиатуру.
Шаг 4. До: 8 картинок по ~158 КБ ≈ 1,2 МБ. После, на телефоне: варианты -800, ~6 картинок ≈ 170 КБ
       (нижние не грузятся из-за loading="lazy"). На компьютере (DPR 1) — варианты -400, ≈ 70 КБ.
       iPad (768, DPR 2): 50vw = 384 × 2 = 768 → вариант 800.
Шаг 6. Первое открытие ~2 с («Загружаем туры…» ≥ 1,5 с), повторное — ~0,1 с, подпись «Показаны сохранённые
       данные (обновлены только что)». При блокировке /api/tours и устаревшем кэше — «Нет связи. Показаны данные,
       сохранённые N мин назад». Минус кэша — устаревшие цены/места; TTL: туры — минуты/часы,
       курс — часы, свободные места — не кэшировать или секунды.
Шаг 7. Картинки при повторном открытии — (memory cache)/(disk cache), передано 0 байт за картинки;
       заголовок Cache-Control: public, max-age=86400. При изменении картинки без смены имени пользователи сутки
       будут видеть старую — поэтому меняют имя (версию) файла.
Шаг 8. В Cache storage kompas-v1: /, /index.html, /style.css, /js/app.js, /api/tours (если запрос шёл через SW),
       просмотренные картинки. Без сети показываются только просмотренные картинки — остальных нет в кэше.
       HTTP-кэшем управляет сервер заголовками, кэшем Service Worker — наш код.
